Improvements

Detailed breakdown — kya kya badla

🛡️
Distributed Rate Limiting
Login abuse prevention — production-grade
❌ Pehle
In-memory counter — server restart pe reset. Multiple server instances pe different counters.
✅ Ab
Redis-backed rate limit. Saare instances ek hi counter share karte hain. Restart ke baad bhi persist.
  • Login: 10 requests / 15 min per IP (Redis key: rl:login:<ip>)
  • General: 200 requests / 1 min per IP (Redis key: rl:general:<ip>)
  • Nginx ke peeche bhi sahi IP detect hota hai (trust proxy: 1)
  • Auto-expire — memory waste nahi
// Before: in-memory (resets on restart) const limiter = rateLimit({ windowMs, max }); // After: Redis-backed (survives restart) store: new RedisStore({ sendCommand: (...args) => redisClient.call(...args), prefix: "rl:login:", })
⚡
API Response Caching
Templates aur static data — 5 min cache
❌ Pehle
Har user request pe DoubleTick ya MailerCloud ka API call. 200 agents = 200+ external API hits per minute.
✅ Ab
Pehli request MongoDB/API se fetch, baaki 5 min tak Redis se serve. <2ms response time on cache hit.
  • GET /api/whatsapp/getAllWhatsappTemplates — 5 min cache
  • GET /api/template/getAllTemplateData — 5 min cache
  • Cache key: URL + query params (unique per route)
  • invalidateCache(pattern) utility — jab template update ho toh clear karo
  • Redis unavailable hone pe graceful fallback — DB se serve
// Sirf yeh ek line add karo route pe: router.get("/getAllWhatsappTemplates", cache(300), // 5 min TTL getAllTemplates );
📧
Bulk Email — Fire & Forget
10,000 emails bhejna — no more timeouts
❌ Pehle
Controller synchronously saare emails bhejta tha. 10k emails = 45+ seconds. Nginx timeout, browser hang, server crash risk.
✅ Ab
200ms mein jobId return hota hai. Background mein batches of 50 bhejta hai. Progress Redis mein track hoti hai.
  • Immediate response: { jobId, totalContacts, templateName }
  • Batch size: 50 emails per batch, 5 concurrent requests
  • 500ms delay between batches — rate limit protection
  • Poll progress: GET /api/jobs/:jobId
  • Job auto-expire: 24 hours (Redis TTL)
// Old: blocking const results = await sendAllEmails(contacts); // 😱 45s wait res.json(results); // New: fire-and-forget const jobId = await createJob("email", contacts.length); res.json({ jobId }); // ✅ 200ms (async () => { ... })(); // background
💬
Bulk WhatsApp — Fire & Forget
DoubleTick bulk send — same pattern
❌ Pehle
WhatsApp controller bhi same problem — synchronous send, browser timeout, koi progress nahi dikhti.
✅ Ab
Turant jobId return, background mein process. DB tracking bhi fire-and-forget — send count par affect nahi karta.
  • DB tracking errors send count affect nahi karte (isolated try/catch)
  • Invalid phone numbers bhi track hote hain — failure reason save
  • DoubleTick messageId se DoubleTickData model link
  • Failure reasons per-batch aggregate hote hain logs mein
📊
Real-time Job Progress Tracking
Frontend ko pata chalega kitna hua
❌ Pehle
Koi tracking nahi. User ko pata nahi — send hua ya nahi, kitne fail hue, kab complete hoga.
✅ Ab
Redis hash mein live progress. Frontend poll kar sakta hai. jobId unique identifier hai per-send-operation.
  • Job structure: { type, total, sent, failed, status, createdAt }
  • Status states: running → completed / failed
  • Redis key: job:email_1710000000_abc123
  • Auto TTL: 24 hours — old jobs automatically clean up
  • Frontend: GET /api/jobs/:jobId se poll karo
// Redis hash structure (per job) { type: "email", total: 5000, sent: 2450, // updates per batch failed: 12, status: "running", // or "completed" createdAt: "2026-03-12T..." }
🔄
Graceful Shutdown
Deploy ke time zero connection leaks
❌ Pehle
Server restart pe Redis connection dangling rehti. PM2 logs mein connection errors aate the.
✅ Ab
SIGTERM/SIGINT pe MongoDB + Redis dono gracefully close hote hain. Zero connection leaks on deploy.
  • disconnectRedis() graceful shutdown sequence mein
  • MongoDB primary + secondary connections bhi close
  • HTTP server pehle close hota hai, tab connections
const gracefulShutdown = async (signal) => { server.close(async () => { await primaryConnection.close(); await secondaryConnection.close(); await disconnectRedis(); // ← new process.exit(0); }); };

Implementation

Kya kya implement kiya — step by step

1. Redis Client Setup config/redis.js
ioredis v5 singleton client — auto-connect, retry strategy (max 5 retries with exponential backoff), graceful disconnect. ENV variables: REDIS_HOST, REDIS_PORT, REDIS_PASSWORD, REDIS_DB.
2. Cache Middleware middleware/cacheMiddleware.js
Generic GET route cache. cache(ttlSeconds) factory function — request URL + query se key banata hai. Cache miss pe DB se fetch, store in Redis. Falls back gracefully if Redis down.
3. Job Tracker utils/jobTracker.js
Redis hash-based job tracker. Functions: createJob(), updateJob(), completeJob(), failJob(), getJob(). 24hr TTL auto-cleanup.
4. Distributed Rate Limiting index.js
rate-limit-redis v4 ke saath RedisStore integrate kiya. Login limiter (10 req/15min) aur general limiter (200 req/min) dono Redis-backed hain.
5. Email Fire-and-Forget controllers/Email/mailerCloudController.js
sendTemplateEmailToCallingData completely rewritten. jobId create karo, 200ms mein response bhejo, background mein batches process karo. updateJob() per batch call hoti hai.
6. WhatsApp Fire-and-Forget controllers/Whatsapp/whatsappController.js
sendTemplateMessage mein same pattern. jobId add kiya, progress tracking, error isolation (DB errors send count affect nahi karte).
7. Route-level Caching doubleTickRoutes.js + templateRoute.js
cache(300) middleware add kiya WhatsApp templates aur email templates routes pe. 5 minute TTL — balance between freshness and performance.
8. Job Status API Endpoint index.js
New endpoint: GET /api/jobs/:jobId. Frontend poll kar sakta hai progress check ke liye. 404 if job not found, 200 with job data if found.

🔑 Key Design Decision: BullMQ nahi liya

BullMQ ek powerful job queue library hai lekin overhead bahut zyada hai. Hamare use case mein simple progress tracking chahiye tha — isliye lightweight Redis hash-based tracker implement kiya. Yeh solution zero extra dependencies, zero worker processes, aur fully custom. Future mein agar proper job queue chahiye toh BullMQ easily add ho sakta hai.
